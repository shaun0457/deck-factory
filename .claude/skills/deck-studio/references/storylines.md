# 故事線骨架

先選骨架，再排頁。每個骨架都寫了適用情境、頁面順序和常見錯誤。

## A. 系統圖主軸（技術設計說明、聽眾混合技術與非技術）

適用：作業說明、架構 review、交付說明、給客戶的技術提案。範例：`assets/open-slide/example/pages.tsx`。

| 順序 | 頁 | 視覺 | 講什麼 |
|---|---|---|---|
| 1 | 封面 | 標題＋一句話主線 | 主線、時長、可隨時打斷 |
| 2 | 現況 | 完成狀態格＋一個關鍵數字 | 做了什麼；難點在哪 |
| 3 | 系統全貌 | 完整系統圖＋流程 ①②③④＋熱點 A/B/C | 只有幾塊、資料怎麼流；接下來放大哪三處 |
| 4–6 | 放大 A/B/C | 縮小系統圖亮起該區＋右側設計＋左下取捨卡 | 做法、為什麼、選擇／沒選／代價 |
| 7 | 怎麼證明 | 系統圖上框出測試範圍＋規則對應測試 | 驗了什麼、沒驗什麼 |
| 8 | 限制與下一步 | 系統圖上用虛線畫出缺的部分 | 已知限制／尚未驗證／下一步；定位一句話 |
| 備用 | 細節頁 | 各自一張圖 | eyebrow 指回對應的主頁 |

- 進度條章節：現況、全貌、A、B、C、證明、限制。
- 熱點最多三個，選「最能展現判斷」的地方，不是程式碼最多的地方。
- 常見錯誤：系統圖只出現一次（後面頁面就脫節了）；每個放大頁塞三個以上的取捨。

### A2. 系統圖主軸＋「我的 N 個設計」（A 的定稿變形，面試設計說明用過）

2026-11 B 版最後的結構，主講 8 頁、7 分 25 秒：

| 順序 | 頁 | 講什麼 |
|---|---|---|
| 1 | 封面 | 一句話主線 |
| 2 | 完成了什麼 | 完成狀態、一個關鍵數字（帶條件）、**沒做的事先講** |
| 3 | 系統全貌 | 用「一次送出」走一遍，不列元件清單；圖上用方形編號標出 N 個設計，右側每個設計寫成一個問題 |
| 4…N+3 | 設計 1…N | 縮小系統圖亮起該區＋取捨卡（Build／Reuse）＋設計本身；按 → 出現它擋住的出事情境和對應的測試 |
| 最後 | 怎麼證明 | 表格每列對應一個設計（同樣的方形編號），寫「怎麼做出這個狀況 → 測試名稱」；CI 分層從「哪些是真的、哪些是假的」推出來 |
| 備用 | 另一份 deck | 旅程頁、細節頁、地端交付等 |

- 「設計」用方形編號，「出事情境」用圓形編號並依品質上色，兩種不會混淆（元件見 `assets/inbox/scenario-evidence/`）。
- 一則訊息沿系統圖走五站的「旅程」很直觀，但當主講太長；最後放進備用頁，被問到「一則訊息怎麼走」時用（元件見 `assets/inbox/journey-morph/`）。
- 最後一頁講完就停在「歡迎從任何一頁開始問」。open-slide 沒有隱藏頁，備用頁要另開一份 deck（`adapters.md`）。

## B. 照需求順序（對答案型）

適用：聽眾手上有一份需求清單，最在意每一項有沒有交代。

1. 封面 → 2. 一頁對答案（需求完成狀態）→ 3…n. 每項需求一節（題目要什麼 → 我做了什麼 → Why so / So what）→ 限制 → 下一步。

- 優點：容易對照。缺點：判斷力被切碎，聽眾要自己拼出全貌。
- 搭配：在第 2 頁後插入系統全貌，或直接改用骨架 A。

## C. 問題驅動（SCQA／金字塔）

適用：提案、決策會議、要說服人選一條路。

1. Situation（現況）→ 2. Complication（變化或問題）→ 3. Question（要決定什麼）→ 4. Answer（建議，先講結論）→ 5–7. 支撐理由（每頁一個）→ 8. 代價與風險 → 9. 需要的決定。

- 標題用結論句；每頁的 So what 要能直接回答 Question。

## D. 前後對照（改版、事故檢討）

1. 原本的樣子 → 2. 出了什麼問題（證據）→ 3. 根因 → 4. 改了什麼 → 5. 改完的證據 → 6. 還沒解決的 → 7. 下一步。

## E. 技術深入（機制優先）

適用：架構 review、技術分享、給工程師的設計說明。論證方式是 instructional。整理自 ppt-master 的 technical-deepdive（見 `ppt-master.md`）。

1. 問題與限制（真正的限制：負載、延遲、一致性、成本、相容性）→ 2. 系統全貌（後面每頁重用這張圖）→ 3. 機制走一遍（跟一條真實路徑，不跳過難的那一步）→ 4. 資料或控制流（請求、資料、失敗三條路分開畫）→ 5. 介面約定（輸入、輸出、錯誤、冪等，配一個真實的呼叫）→ 6. 取捨比較（只比真正影響決定的軸）→ 7. 失敗模式（觸發、影響範圍、偵測、恢復）→ 8. 量測證據（工作負載、環境、版本、變異）→ 9. 導入或遷移路徑 → 備用：參考細節。

- 規格、目前實作、量測、個人意見要分開講；計畫中的設計不能講成已上線。
- 圖和它的說明放同一頁。

## F. 提案（給客戶或主管，要對方簽下去）

適用：解決方案提案、PoC 提案、FDE 對客戶的交付計畫。論證方式是 pyramid。整理自 ppt-master 的 solution-proposal。

1. 對方的現況（用對方的說法和數字）→ 2. 需求解讀（要解什麼、成功標準）→ 3. 建議做法（先講結論，每一項對到一個需求）→ 4. 考慮過的替代方案 → 5. 方案架構（標出既有、新做、第三方）→ 6. 交付計畫（階段、相依、決策點、對方要參與的地方）→ 7. 團隊與責任 → 8. 實績（一個講深的案例勝過一排 logo）→ 9. 費用 → 10. 風險與對策（含對方那邊的風險）→ 11. 假設與相依 → 12. 下一步（誰、做什麼、哪天）。

- 標題寫「對方得到什麼」，不寫「我們有什麼能力」。
- 包含的、加價的、假設、排除項目要分開寫清楚，這些不清楚之後會變成爭議。
- 最後一頁是具體的下一步，不是「謝謝」。

## G. 教學或工作坊

適用：內部訓練、客戶上線培訓。論證方式是 instructional。整理自 ppt-master 的 workshop-teaching。

1. 學完能做到什麼（寫成看得到的動作）→ 2. 前置條件（版本、權限、環境，附驗證方式）→ 3. 最少的概念（一張圖或一個比喻）→ 4. 完整示範（真實輸入和輸出，不省略步驟）→ 5. 練習（任務、起點、成功條件、卡住去哪找）→ 6. 常見錯誤（錯的結果和原因，對照正確的）→ 7. 速查卡 → 8. 檢查有沒有學會（問應用，不問記憶）→ 9. 回顧與下一步。

- 規則、慣例、建議、個人偏好要講清楚是哪一種；簡化過的地方要標明。

## 先選論證方式，再選骨架

| 要聽眾 | 論證方式 | 骨架 |
|---|---|---|
| 理解一個系統或技術 | instructional | A、A2、E |
| 學會做一件事 | instructional | G |
| 做決定、核准、簽約 | pyramid | C、F |
| 對照清單、知道進度 | briefing | B |
| 理解一次改版或事故 | narrative 或 pyramid | D |

視覺風格（配色、字體）和論證方式分開決定。

## 標題風格

| 風格 | 範例 | 適合 |
|---|---|---|
| 主題式 | 「API 的 5 個動作設計」 | 聽眾想對照清單；講者不想顯得太強勢 |
| 結論式 | 「規則交給資料庫：重送、同時送、當機都擋得住」 | 時間短、要聽眾帶走判斷 |

主標題約 21–28 字以內（60 px、1680 px 寬時一行）。不確定時做 A/B。
